# CSPRNG-1.3A Focused Threat Model

## Scope

This threat model covers only Mosera's canonical `INTERNAL_CSPRNG` path from immutable draw execution manifest through OS entropy acquisition, HMAC_DRBG session use, sampling, provider evidence, Outcome Certificate binding, and canonical outcome persistence. It is an internal review artifact, not independent certification.

## Assets and Boundaries

Protected assets are outcome unpredictability before publication, one-result authority per draw, DRBG Key/V and initialization material, immutable provider/certificate evidence, exact provider selection, and replay/idempotency integrity.

Trust boundaries are the Game Engine process, .NET cryptography, the host OS cryptographic RNG, PostgreSQL/advisory locking, production signing, the container/host boundary, and privileged operational execution. Mosera controls application validation and persistence; it does not independently validate the OS entropy implementation or .NET HMAC internals.

## Threat Matrix

| Threat actor/event | Attack | Existing control | Residual risk | Control owner / dependency |
| --- | --- | --- | --- | --- |
| Malicious player | Predict a future draw from published outcomes | Fresh OS input, isolated per-draw HMAC_DRBG state, immediate reseed, no state persistence | Depends on OS entropy and HMAC implementation; HIGH conformance gaps must be remediated | Mosera plus OS/.NET |
| Malicious operator | Select a favorable provider or replace generated numbers | Exact immutable manifest binding, governed activation, canonical result hash, certificate and canonical outcome binding | Host/process compromise can act before controls; operational governance and signing remain critical | Mosera |
| Compromised application user | Call arbitrary RNG or supply provider selection | No arbitrary-byte API; canonical endpoint resolves manifest-bound provider; operational security gate | Internal code can still call the low-level runtime and misuse missing limits | Mosera; CSPRNG-1.3A-F001/F002 |
| Compromised database | Replace evidence or bind another draw | Append-only constraints, exact manifest/provider/certificate foreign validation, canonical payload hashes | Database superuser or migration privilege can bypass triggers; external signed/WORM evidence is not established | Mosera operations / future WORM |
| Compromised application process | Read entropy, Key/V, or generated bytes in memory | Short per-draw lifetime, finally-based destruction, explicit zeroing | A live process compromise can read current state and output; managed/runtime copies and dumps may remain | Host/runtime security |
| Compromised host | Subvert OS entropy or inspect all process memory | Application fails closed on API errors; no deterministic fallback | A malicious kernel defeats entropy and memory assumptions; not mitigated inside the application | Platform certification / host security |
| Malicious insider | Activate unreviewed configuration or extract evidence | Versioned provider/configuration, readiness, operational security, append-only audit | Privileged database/host access remains a high-trust role | Mosera governance |
| Concurrent request attacker | Race two executions for one draw | Manifest-scoped PostgreSQL advisory lock, unique idempotency/manifest constraints, duplicate returns persisted result | Availability denial by lock contention; no shared DRBG session observed | Mosera/PostgreSQL |
| Replay attacker | Re-submit an old request/result for another draw | Canonical request hash binds manifest/draw/provider/configuration; certificate draw/hash checks | Hash/canonicalization regressions require continued QA | Mosera |
| Deployment/configuration mistake | Enable test provider, wrong provider version, or unsafe in-memory persistence | Exact activation/readiness checks, durable PostgreSQL required, no fallback between categories | Operators can still misconfigure host/runtime version or image; release evidence must pin artifacts | Mosera release governance |
| Entropy-source failure | Return no bytes, partial bytes, or unsupported platform | Linux loops partial reads; all APIs throw on failure; unsupported OS throws; no fallback | API success does not prove entropy quality; underlying OS catastrophic failure may be undetectable | OS/platform / external validation |
| RNG state disclosure after output | Recover previous outputs | Post-output HMAC_DRBG Update gives backtracking resistance under HMAC assumptions | Managed copies and the current output buffer may remain; prior state compromise is different | Mosera/.NET |
| RNG state disclosure before output | Predict current/future session output | Per-draw session limits blast radius; fresh sessions isolate other draws | Current draw and remaining session output are compromised until destruction | Host/process security |
| VM/container snapshot rollback | Duplicate kernel RNG or application state | No application DRBG state survives process restart; fresh getrandom calls | Host entropy behavior under cloned/snapshotted kernels is a platform assumption; active process snapshots can capture state | Infrastructure/platform |
| Signing-key compromise | Authorize substituted certificates | Exact signing provider/version/key binding | A valid compromised signing key can authorize false evidence; key rotation/revocation and HSM/KMS controls are outside CSPRNG | Signing authority |

## State-Compromise Conclusions

1. State learned after a completed Generate does not directly reconstruct prior HMAC_DRBG state under the HMAC one-way assumption because Generate performs the prescribed post-output Update.
2. State learned before Generate exposes that draw's next output and subsequent output until reseed/destruction.
3. One session compromise does not derive another session under the assumption that separate OS reads are unpredictable and the OS does not repeat initialization material.
4. Process compromise can capture raw input/state before zeroization. Application zeroization is not a defense against a live privileged memory reader.
5. Persisted evidence contains no raw entropy, nonce, reseed bytes, Key, or V. The persisted production `SeedIdentifier` is an unnecessary hash of secret initialization material and should be removed in a versioned remediation.

## Fail-Closed Conclusions

Entropy acquisition, unsupported platforms, health-check failures, invalid generation definitions, provider mismatch, lock/persistence failure, request conflicts, certificate mismatch, and canonical payload mismatch abort the authoritative path. No deterministic entropy fallback or alternate provider fallback was found. The standards-envelope defects in CSPRNG-1.3A-F001 and F002 are different: the runtime accepts invalid parameters rather than rejecting them, so the implementation is not sufficiently misuse-resistant or standards-conforming.

## Certification Dependencies

- Accepted evidence for the deployed OS entropy source and security boundary.
- Accepted evidence for .NET/platform HMAC-SHA-256 implementation.
- Remediated and re-reviewed SP 800-90A limits and parameter enforcement.
- Traceable authoritative DRBG vectors and, where required, CAVP/CMVP validation.
- Production-grade immutable/WORM retention for formal evidence exchange.
- Independent cryptographic specialist/laboratory review of the remediated frozen source and deployment boundary.
